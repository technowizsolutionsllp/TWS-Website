# Admin area: operator guide

The `/admin` pages for the operator: Insights (trials and app telemetry), Records (find and delete trial records) and the Health check. For how they fit into the system see [ARCHITECTURE.md](ARCHITECTURE.md#6-admin-area); for the telemetry definitions behind the charts see [PINCHPDF_TELEMETRY.md](PINCHPDF_TELEMETRY.md). Code: `lib/admin/*`, `app/admin/*`, `lib/trial/metrics.ts`.

## Pages (`/admin`)

- `/admin` is a home page with a card for each sub-page. `/admin/insights` has six tabs (`?tab=trials|buying|licenses|devices|installs|scans`): **Trials** shows trial and request statistics (the original page), **Buying**, **Licenses** and **Devices** show the app telemetry (abandoned buys, active licenses by plan, deactivations and key changes; see `docs/PINCHPDF_TELEMETRY.md`), **Installs** shows installs by kind and uninstalls reported by the installers, and **Scans** shows NoDupe's scan counts per mode (NoDupe only). All tabs share a product selector (PinchPDF, NoDupe, all products: each product is read from its own database and "all" combines them) and any date range up to 366 days (`?product=all&from=2026-10-01&to=2026-10-31`). Ranges over 120 days are shown as weekly totals. All days are UTC.
- Protected by HTTP Basic authentication against the `ADMIN_USER` and `ADMIN_PASSWORD` Worker secrets. Add them as type **Secret**, never as a plain Variable (a deploy removes dashboard-only variables). **If either is unset, or the password is shorter than 8 characters, the pages answer 404.** A longer password is better. Logins are throttled per IP by `TRIAL_ADMIN_LIMITER`.
- **Trials tab, requests:** the "Requests per day" chart has a series per trial endpoint, including `lookup` (revision 5: the app asks whether the computer already has a trial). The register outcomes include `restored` (a recognised computer continued its trial) next to `registered` and `already_used`.
- Insights shows only aggregate numbers: no names, emails, device hashes or trial ids. (Records, below, is the one page that shows a name and email.) The pages run no scripts and are served with `no-store`, `noindex` and a strict CSP.
- **The migrations must be applied to both databases** (`npx wrangler d1 migrations apply pinchpdf --remote`, and `... apply nodupe --remote`). For PinchPDF, 0002 adds `trials.product` (existing rows become `pinchpdf`) and the `metrics_daily` counters, 0003 the three telemetry tables and 0004 the install events column. NoDupe's `0002_trials_and_telemetry.sql` creates all of those, plus its per-mode trial counters, in one step. Until they are applied the pages still load and say what is unavailable (request counts, or telemetry), and counting is skipped quietly. Telemetry requests are counted as the `telemetry` series in the requests chart.
- **Request counts are approximate and start when this version goes live.** Handlers tag each response with the result code they already log; `lib/trial/metrics.ts` keeps counts in memory and writes them in small batches (at most one batch per instance every 10 seconds), so a flood of bad requests cannot use up the D1 write allowance and a metrics failure never fails a trial request. A few counts can be lost when an instance restarts.
- **Two products, two databases.** NoDupe runs the same trial and telemetry service as PinchPDF (`/api/nodupe/trial/v1/...`), in its own D1 database `nodupe` (binding `NODUPE_DB`), with one trial counter per scan mode (5 Basic, 3 Similar, 1 Deep). A product view reads only that product's database. If a database is not bound, its product view answers 503 and All products shows the other with a notice. The update-check counters (`update_check`, both products) stay in the PinchPDF database, because the update Worker binds only that one.

## Records (`/admin/records`)

Find the person behind a free trial and erase or delete the record, to answer a deletion request (Privacy 10.6). Same admin login as the other pages.

- **Search** by name, email, support reference or trial id, for PinchPDF, NoDupe or both. A full email address is looked up exactly (case-insensitive, through the blind index). Anything else matches anywhere in the decrypted name or email of the newest 20,000 records of a product (name and email are encrypted, so this cannot be done in SQL), or exactly on the 8-character support reference or the trial id. At least 3 characters; at most 25 matches are shown. Search and deletion are POST forms, so a name or email never appears in a URL, log or browser history.
- **Continued trials (protocol revision 5).** A record whose trial was continued on its computer after a reinstall shows "Continued once" (or N times), the date of the last one and how it was recognised (the support reference from the app's lookup, or the same email). Each continue moved the trial to a new install key, so an earlier install of the app no longer reports usage: that explains a user who says an old install stopped syncing. The JSON API returns the same as `restores: [{at, matched_by}]`. The audit rows (`restore`, operator `service`) hold the counts before and the replaced install key, never a name or email.
- **Erase name and email** clears the encrypted name, email and email index and keeps the row: the computer keeps its used scans and cannot start another free trial. Use this for most requests.
- **Delete whole record** removes the row, including the device hashes. That computer can then register a new free trial. Telemetry events (no name or email) are not touched; they follow their own retention.
- Each deletion needs a reason (3 to 500 characters) and, on the page, the typed support reference. The change and its `trial_audit` row (`erase-contact` or `delete-all`, operator `admin-ui` or `admin-api`, the reason and the previous counts, never a name, email or hash) are written in one batch. **Every record whose name or email is shown is also audited** (`view-contact`), and nothing is shown if that audit write fails.
- Requests from another site are refused (`Origin` check), because browsers send saved Basic credentials on cross-site requests.
- **JSON API** (in Swagger under each product): `POST /api/pinchpdf/records/v1/search` and `.../delete`, and the same under `/api/nodupe/records/v1/`. Bodies: `{"q": "..."}` and `{"id", "action": "erase_contact"|"delete", "reason"}`. Needs `PII_KEY` and `PEPPER_EMAIL` (the trial secrets) and the product's database.
- `scripts/trial-admin.mjs` (`erase-contact`, `delete-all`, `export-contact`) still works and writes the same audit entries.

## Checkout links (`/admin/checkout`)

Sets where the Buy buttons in PinchPDF and NoDupe send buyers, per product and per mode (Live, and Test for debug builds):

- the primary provider (Dodo Payments or Lemon Squeezy) and Force (no backup);
- up to 4 link sets, each link with its own license type;
- promotions with optional start and end dates (UTC), which may not overlap;
- discount codes in the links.

Every change is checked against the provider's real checkout page before it is saved. In Live, a failed check blocks the save; in Test it is a warning. Each save goes through a review page that needs a reason, and in Live, when what buyers get changes, a tick confirming that you opened the new pages. Nothing is served from here until a setting is saved: until then the apps' built-in links stay in use.

**Migrations:** apply `migrations/0005_checkout_links.sql` and `migrations-nodupe/0003_checkout_links.sql`. Until they are applied, the page answers 503 and the public checkout endpoints answer 503; the apps keep their built-in links.

Details, the rules and the app contract: [CHECKOUT_LINKS.md](CHECKOUT_LINKS.md).

## Health check (`/admin/health`)

Open it from the **Health check** card on `/admin` (same login as the other admin pages). It shows a green, amber or red indicator for every item, grouped by category, with the error when something is wrong. It refreshes on demand (**Run health check**) or automatically (30 s, 1 min or 5 min).

- **Configuration and services** (checked on the server, for each product: the D1 binding and a query, that the tables and migrations exist (NoDupe also its per-mode counters), the trial secrets and settings (present and well formed, names and reasons only; NoDupe has its own terms and privacy version settings), and trial and telemetry retention, see [RETENTION.md](RETENTION.md)): the rate-limit bindings, including the two telemetry limiters (amber when missing), telemetry retention (amber when events older than the retention period plus 30 days remain: run the purge), app updates (amber until `PINCHPDF_RELEASES_REPO`, `NODUPE_RELEASES_REPO` and `RELEASE_PUBLIC_KEY` (one or several public keys, comma-separated) are valid and a valid list is published in the releases repository, and when a list has invalid entries or the last good list is being served because GitHub could not be read), the email settings for the contact and support forms (the mailer is *not* called, so no email is sent), and the API docs login. For each product, **Checkout links** says what the Buy buttons open in Live and Test. It is red when the saved setting cannot be read, or when Live has no link for a license.
- **Trial API self-test** (on the server, for PinchPDF and NoDupe): the server plays the app against its own handlers: a challenge, then a sealed `register` request (refused before any database access), a sealed `lookup` request with random device hashes (reads D1, answers `none`) and a sealed `usage` request for a trial that cannot exist (reads D1), for every accepted key id. It writes nothing. It also shows the **server public key for each key id**: the PinchPDF and NoDupe apps must both embed exactly that value (the two products share the server keys), because the server cannot see which key an app holds. A mismatch makes every register and usage request fail with a 400.
- **Endpoint and page probes** (sent by your browser over the public internet, so they cover DNS, Cloudflare and the Worker): the trial endpoints (`register`, `lookup`, `usage`) and the telemetry endpoint of each product (GET must answer 405), the two update-check endpoints (200 once set up; 503 shows amber until the releases repository and key are configured), the contact and support APIs, admin, the Insights JSON API and docs (a login prompt, 401, means up and protected), every website page (built from the product and legal data, so new pages are included automatically) and the site files. Only the stateless `challenge` endpoint gets a real POST. The other POST-only routes are probed with GET and must answer 405, which proves the route is live without touching rate limiters, the database or email. 429 shows amber (reachable, throttled).
- The probes send `x-tws-health: 1`, which the request counters ignore, so health checks never appear in Insights. The counters are not a security control; the header changes nothing else.
- `GET /admin/health?format=json` returns the server checks as JSON (used by the page to refresh).
